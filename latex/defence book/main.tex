\begin{abstract}
Defect classification turns isolated bug reports into process-level signals that guide debugging strategy, resource allocation, and quality improvement. Defects4J is the standard empirical benchmark for Java fault studies, yet no prior work has labelled it with a principled, semantic taxonomy. Existing classification efforts cover only tens to a few hundred bugs, rely on structural or patch-shape taxonomies that describe \emph{how} a bug manifests rather than assigning it a semantic defect type, or depend on post-fix code, which is unavailable during real triage.

This thesis presents an automated pipeline that classifies Defects4J bugs into the seven Orthogonal Defect Classification (ODC) Design/Code defect types using Large Language Model (LLM) reasoning. We structure classification as a two-variable experimental design: a \emph{taxonomy} axis, which controls the label space the model may answer in, crossed with a \emph{strategy} axis, which controls how the model reasons toward a label. The strongest strategy is an enforced reasoning loop, inspired by scientific debugging, in which the model commits to a hypothesis and then probes held-back evidence to confirm or refute it. An explicit ``Other'' escape category lets us measure the coverage of the taxonomy instead of assuming it. We classify every bug in two evidence modes, pre-fix (symptoms only) and post-fix (with the buggy-to-fixed diff), which provides an evaluation reference for a benchmark that carries no ODC labels.

We evaluate the pipeline on 410 bugs from six Defects4J projects, giving 1{,}640 classifications. Three ODC types account for 97.8\% of the bugs, and under the default condition the type distribution does not differ significantly across projects. The ``Other'' category was available in every classification and was never selected, which bounds the true escape rate at 0.2\%. A classification made from pre-fix evidence reproduces the fix-informed reference on 70.2\% of bugs (Cohen's $\kappa = 0.505$), and is unrelated to it on only 2.4\%. The enforced loop significantly improves chance-corrected agreement over a strong few-shot prompt and achieves higher agreement in all six projects. Roughly 30\% of labels change once the fix becomes visible, but 80\% of those changes remain within the same three closely related defect types, and the aggregate type distribution remains almost unchanged. Running the pipeline with a second model, gpt-5-mini, on the manually analysed scenario bugs shows that the pre-fix advantage of the loop and the main failure modes arise from the pipeline, while the loop's use of the fix diff depends on the model.
\end{abstract}

\chapter{Introduction}

Software bugs are an unavoidable part of the development process. Even carefully written programs contain defects that cause unexpected behaviour, crashes, or incorrect results. Identifying a bug is only the first step. Understanding what kind of bug it is, why it happened, and how it should be fixed is equally important for improving software quality over time \cite{catolino2019not}. Different defect types call for different debugging strategies, resource allocations, and repair approaches \cite{catolino2019not, hirsch2022using}.

In practice, developers spend a significant portion of their time triaging and debugging reported issues. Bug categorization makes this process more efficient by grouping defects into meaningful categories that guide debugging strategies and resource allocation \cite{andrade2025empirical}. Early prediction of a bug's category from its report helps teams prioritize work before examining the code \cite{hirsch2022using}. Structured categorization also provides actionable measurements that managers and developers can use to improve their processes \cite{chillarege1992odc}. This process-level use depends on labels that are consistent and comparable across bugs, so that a collection of classified defects can be aggregated to reveal which kinds of mistake a development process keeps producing.

Manual triage still gives the best results, but it does not scale to large benchmark datasets \cite{andrade2025empirical}. Evaluating automated classification therefore requires a dataset that is large enough to support general conclusions and rich enough in evidence to classify from.

\section{Defects4J: The Benchmark Dataset}

Defects4J is a curated database of real, reproducible Java bugs paired with developer-written patches and regression test suites \cite{just2014defects4j}. It contains over 830 active bugs across 17 open-source Java projects and serves as a standard benchmark for empirical software engineering research, including fault localization, automated program repair, and testing studies \cite{rafi2024revisiting, durieux2018automatic}.

Every bug in Defects4J comes with a rich set of artifacts: the original bug report, the triggering tests that expose the bug, the buggy and fixed source code, and the buggy-to-fixed diff. These artifacts provide several independent perspectives on the same defect. A stack trace shows where the program failed, a bug report describes what the user observed, a failing test states the expected behaviour, and a diff shows what the developer eventually changed. This richness makes Defects4J particularly well suited for automated classification research.

One property of Defects4J is central to the evaluation in this thesis. Because every bug ships with the developer's actual fix, we can construct two versions of the same case file that differ in exactly one respect: whether the fix is visible. We refer to these as the \emph{pre-fix} and \emph{post-fix} versions of a bug, and define them precisely in Section~\ref{sec:prefix_postfix}. This controlled difference provides an evaluation reference in a dataset that carries no ODC labels, and Section~\ref{sec:eval} develops it into the evaluation framework used throughout this thesis.

\section{Motivation}

Despite the widespread use of Defects4J in software engineering research, no study has fully classified its bugs using a principled, semantic taxonomy. Existing classification efforts fall into three groups, each with a different focus and a different limitation.

First, structural approaches such as the work of \textcite{vanderspuy2025anatomy} classify bugs by their control-flow and data-flow graph representations. This work covers 488 bugs, but it captures how bugs manifest syntactically rather than why they exist semantically. A missing null check and an omitted feature can produce similar control-flow changes while representing fundamentally different defect causes.

Second, patch-level taxonomies such as the Defects4J dissection by \textcite{sobreira2018dissection} classify repair actions for 395 bugs from an older version of the dataset. This describes what developers changed, not the defect mechanism that made the change necessary.

Third, small-sample inspections such as the work of \textcite{jiang2019manual} manually analyse 50 bugs. The analysis is detailed, but the approach does not scale to the full benchmark.

None of these approaches classifies bugs into a semantic defect-type taxonomy at the scale of the full benchmark. This gap motivates an automated, scalable classification approach that goes beyond structural and patch-level patterns.

Large Language Models (LLMs) offer a promising way to address this gap. Recent work shows that code-aware LLM reasoning can classify software artifacts competitively, provided the prompt is designed well \cite{colavito2024llm, koyuncu2025exploring, nong2024cot}. Left unconstrained, however, LLM classification suffers from label inconsistency: with no fixed label space, different runs assign incompatible categories to the same bug \cite{koyuncu2025exploring}, and the resulting labels cannot be aggregated or compared. Supplying a taxonomy, and defining its labels explicitly, measurably changes what the model predicts \cite{li2024knowbug}. Orthogonal Defect Classification (ODC) provides such a taxonomy, classifying each defect into one of seven Design/Code defect types that capture the semantics of the bug itself \cite{chillarege1992odc, ibm2013odc}. Pairing LLMs with ODC turns classification into a bounded, semantically grounded decision problem.

A forced, fixed schema, however, introduces the opposite failure: it manufactures false certainty for defects that do not fit any of its categories. We therefore treat the coverage of the taxonomy as something to measure rather than assume, by giving the model an explicit escape category, ``Other''. A defect that falls outside the seven types becomes recorded data instead of a mislabelled forced choice.

\paragraph{Pre-fix and post-fix classification.}
\label{sec:prefix_postfix}
In this study, every bug is classified twice, from two versions of the same evidence that differ in exactly one respect.

\begin{itemize}
    \item \textbf{Pre-fix classification} uses only the evidence available before the defect is repaired: the bug report, the failing tests, the exception and stack trace, and the relevant source-code context around the failure. This is the situation a developer faces during triage, before anyone has written a fix, and it is the classification the pipeline is intended to produce.
    \item \textbf{Post-fix classification} uses the same evidence together with the developer's actual fix, in the form of the buggy-to-fixed code diff that Defects4J provides for every bug. Everything else in the evidence is identical.
\end{itemize}

Because an ODC defect type describes the nature of the correction made to fix a bug, the post-fix classification is the better-informed of the two. Since Defects4J carries no ground-truth ODC annotations, we therefore use the post-fix classification as a fix-informed evaluation reference: comparing the pre-fix and post-fix classifications of the same bug shows how well a label assigned before the fix agrees with a label assigned once the fix is known. We compare the two labels at four tiers: whether they assign the same type (strict match), whether either type appears among the alternative types listed by the other classification (top-2 match), whether both types belong to the same broad group of related ODC types (family match), and Cohen's $\kappa$, which corrects strict agreement for the agreement expected by chance. When the two labels differ for the same bug, we refer to this as \emph{drift}. Section~\ref{sec:evidence_modes} describes how the two evidence modes are constructed, and Section~\ref{sec:eval} develops their comparison into the evaluation framework.

\paragraph{Classification conditions.}
\label{sec:conditions_intro}
Each classification is made under a \emph{condition}, defined by two independent choices. The \textbf{taxonomy} determines the label space: \textit{free}, in which the model describes the defect in its own words; \textit{closed}, in which it must select one of the seven ODC types; or \textit{open}, in which it may also select the ``Other'' escape category. The \textbf{strategy} determines how the model reasons: \textit{zero}, a single plain prompt without a taxonomy or examples; \textit{few}, a single prompt with type definitions, a decision checklist, and worked examples; or \textit{scientific}, an enforced reasoning loop in which, on every turn, the model states a hypothesis about the defect type and a prediction, and then either requests a specific piece of additional evidence, called a \emph{probe}, or concludes. A condition is named by its strategy and taxonomy, such as \textit{scientific-open}, which is the default condition in this thesis. Section~\ref{sec:conditions} defines the valid conditions, and Section~\ref{sec:loop} describes the reasoning loop.

\section{Problem Statement} \label{sec:problem}

This section defines the specific research gap that this thesis addresses and formally states the problem we aim to solve.

\subsection{Limitations of Existing Approaches}

Current attempts at classifying Defects4J bugs suffer from five limitations:

\begin{enumerate}
    \item \textbf{Coverage gap:} No study has fully labelled the active Defects4J set. Existing work covers only tens to a few hundred bugs \cite{sobreira2018dissection, vanderspuy2025anatomy, jiang2019manual}.
    \item \textbf{Structural-only labels:} Control-flow and data-flow analyses capture how bugs manifest syntactically, not the defect type they belong to \cite{vanderspuy2025anatomy}.
    \item \textbf{Patch-focused taxonomies:} Repair-action classification describes fix patterns, not the underlying defect mechanism \cite{sobreira2018dissection}.
    \item \textbf{Post-fix dependency:} Machine learning approaches require labelled training data, which Defects4J does not have for ODC, or access to post-fix code, which limits their applicability to pre-triage scenarios \cite{thung2012automatic}.
    \item \textbf{Evaluation scarcity:} Without ODC ground truth, there is no practical evaluation framework for large-scale automated classification \cite{andrade2025empirical}.
\end{enumerate}

\subsection{The Research Gap}

No study has produced a context-aware, semantically grounded, scalable classification of Defects4J. Addressing this gap requires a solution that is:

\begin{itemize}
    \item \textbf{Context-aware:} using multi-modal evidence from code, tests, bug reports, and stack traces, rather than a single information source.
    \item \textbf{Semantic:} classifying defects by their defect mechanism, not by syntactic patterns.
    \item \textbf{Taxonomy-constrained:} using a principled framework such as ODC to prevent label inconsistency and to make results comparable across studies.
    \item \textbf{Open to its own limits:} able to record a defect that does not fit, rather than forcing it into the nearest category.
    \item \textbf{Scalable:} using LLM-based reasoning to classify at benchmark scale without manual labelling.
    \item \textbf{Evaluable without ground truth:} providing its own evaluation reference, since Defects4J supplies none.
\end{itemize}

\subsection{Problem Definition}

Given these limitations, we define the problem as follows: \emph{how can we classify Defects4J bugs into ODC Design/Code defect types from pre-fix evidence alone, while also being able to evaluate that classification without ground-truth labels?}

The four research questions of Section~\ref{sec:rqs} decompose this problem into measurable parts. Our guiding intuition is that pre-fix classification is a prediction made from symptoms alone, while post-fix classification is a reference made with the fix visible; agreement between the two indicates that the prediction is stable enough to justify operational use of the pre-fix signal.

\section{Research Objectives}

This thesis addresses the following four research objectives:

\begin{enumerate}
    \item[\textbf{RO-1:}] Build an automated pipeline that classifies Defects4J bugs into ODC defect types using LLM reasoning grounded in evidence the model must actively request.
    \item[\textbf{RO-2:}] Collect bug evidence in two modes, pre-fix (symptoms only) and post-fix (with the actual code fix), mapping Defects4J artifacts onto ODC's opener and closer attributes, which are the attributes recorded when a defect is found and when it is fixed.
    \item[\textbf{RO-3:}] Separate the label space the model uses from the way it reasons toward a label, producing a small set of controlled, comparable classification conditions.
    \item[\textbf{RO-4:}] Design a four-tier evaluation framework that compares pre-fix and post-fix classifications using strict match, top-2 match, family match, and Cohen's $\kappa$.
\end{enumerate}

\section{Research Questions}
\label{sec:rqs}

We evaluate these objectives through four research questions.

\begin{description}
    \item[RQ1: Defect-type distribution across projects.] What is the distribution of ODC defect types across the Defects4J benchmark, and does this distribution vary significantly across projects?

    \item[RQ2: Coverage of the ODC taxonomy.] Do the seven standard ODC defect types cover all the bugs in Defects4J, or do some bugs fall outside them and require the ``Other'' escape category?

    \item[RQ3: Classification accuracy.] Treating the post-fix classification as a fix-informed reference, how often does the pre-fix classification assign the same defect type, and when it does not, how far apart are the two labels under a four-tier evaluation?

    \item[RQ4: Contribution of each component.] \textbf{RQ4a:} What does explicit ODC taxonomy grounding contribute, compared with letting the model describe the bug in its own words? \textbf{RQ4b:} What does the enforced hypothesis--prediction--probe--observation loop contribute over a strong single-call few-shot prompt, when both use the same taxonomy?
\end{description}

RQ1 and RQ2 characterize the dataset and the fit of the taxonomy to it; RQ3 measures how closely the default configuration reproduces the fix-informed reference and how the labels change when the fix is visible; and RQ4 isolates what each structured component contributes.

\section{Contributions}

The main contributions of this thesis are:

\begin{itemize}
    \item We separate the label space the model uses (the taxonomy) from how it reasons toward a label (the strategy), giving a small set of controlled, comparable conditions instead of one all-in-one prompt.
    \item We give ODC an open ``Other'' escape category that requires a written justification, which turns the coverage of the taxonomy into something we measure directly instead of assume.
    \item We build an enforced scientific reasoning loop, adapted from fault localization to defect-type classification, in which the model has to commit to a hypothesis and probe held-back evidence before it is allowed to conclude, leaving a full, auditable reasoning transcript.
    \item We classify every bug in two evidence modes, pre-fix and post-fix, mirroring ODC's opener/closer split, which lets us evaluate the pipeline without ground-truth labels.
    \item We report a quantitative evaluation over 1{,}640 classifications of 410 bugs from six projects, with confidence intervals, permutation tests, and paired bootstrap comparisons.
    \item We run the pipeline with two LLMs and separate the behaviours that arise from the pipeline from those that depend on the model.
\end{itemize}

\chapter{Related Works} \label{chapter:related}

This chapter reviews the existing literature that forms the foundation of our research. We organize the review around five themes: existing attempts at classifying Defects4J bugs, LLM-based defect classification, the need for a principled taxonomy, the Orthogonal Defect Classification framework that our pipeline adopts, and human agreement on ODC labels.

Defects4J \cite{just2014defects4j} is one of the most widely used benchmark datasets for software debugging and defect analysis research. It provides a curated collection of reproducible real-world bugs from 17 open-source Java projects, along with their original bug reports, reproducible failures, buggy and fixed source code, and buggy-to-fixed patches. This rich and reproducible set of artifacts makes Defects4J particularly suitable for automated defect classification. In this research, we leverage these artifacts to investigate the classification of Defects4J bugs into ODC defect categories using LLMs.

\section{Existing Defects4J Bug Type Classification}

Several studies have attempted to classify bugs in the Defects4J dataset, each using a different approach and covering a different subset of the data.

\textcite{vanderspuy2025anatomy} manually classified 488 faults using control-flow and data-flow graph abstractions, identifying six control-flow and two data-flow categories. This structural perspective provides insight into how defects alter program execution; however, it does not necessarily capture the underlying reason for the defect. For example, a missing null check and an omitted feature may result in similar control-flow changes while representing fundamentally different defect causes.

\textcite{sobreira2018dissection} analysed 395 bugs from Defects4J v1.2, focusing on repair actions and patch patterns. Their findings showed that a substantial proportion of patches involve modifications to conditional blocks. Although patch-based analysis is valuable for understanding how developers repair defects, patch characteristics primarily describe the changes made to the program rather than the underlying defect mechanism that necessitated those changes.

\textcite{jiang2019manual} manually examined 50 Defects4J bugs to investigate test-suite quality and fault fixability. While their analysis provides detailed insights into individual defects, the relatively small sample limits the generalizability of the findings to the broader Defects4J dataset.

These studies provide valuable perspectives on defect structure, repair actions, and fixability. However, they examine relatively limited subsets of Defects4J, rely primarily on code-structural or patch-based taxonomies, and do not apply a semantic defect-type taxonomy to the full set of bugs. Our work addresses this gap by investigating ODC-based semantic defect classification across the Defects4J dataset using LLMs.

\section{LLM-based Defect Classification}

Recent studies have demonstrated that LLMs can effectively classify software defects when provided with relevant contextual information.

\textcite{colavito2024llm} showed that LLMs can classify issue reports, which are closely related to bug reports, with reasonable accuracy, validating the basic hypothesis that LLMs are suitable for defect classification tasks. \textcite{koyuncu2025exploring} extended this by using LLMs and several prompt engineering techniques, including few-shot, chain-of-thought, tree-of-thoughts, and plan-and-solve prompting, to achieve fine-grained bug report categorization.

\textcite{li2024knowbug} and \textcite{du2024llm} use LLMs, leveraging several prompting strategies, to classify bug reports into categories based on their behaviour and reproducibility. These studies showed that LLMs benefit from structured prompting strategies, ranging from simple task prompts to reasoning-based approaches such as chain-of-thought and tree-of-thought, enriched with few-shot examples and domain knowledge integration, to improve the accuracy, generalization, and interpretability of bug report categorization. \textcite{nong2024cot} similarly showed that chain-of-thought prompting substantially improves LLM performance on vulnerability analysis.

Relatedly, \textcite{kang2023autosd} incorporated scientific debugging into LLM prompting through AutoSD. In their approach, the model formulates a hypothesis, performs a debugging experiment to test it, and uses the resulting evidence to determine whether the hypothesis is supported, primarily for explainable fault localization. \textcite{kang2024autofl} later extended this direction to a tool-using setting, in which the LLM gathers code and test evidence on demand through function calls rather than receiving a fixed context. Building on these ideas, our iterative reasoning process uses targeted probes of the collected evidence to evaluate competing hypotheses and ultimately classify the defect according to ODC type. The difference lies in the task: these works use evidence to decide \emph{where} a fault is, whereas we use it to decide \emph{what kind} of defect it is.

Compared with traditional machine learning approaches, LLMs offer a key advantage in their ability to jointly interpret natural-language and source-code information. Earlier automated ODC classification systems based on SVM and Naive Bayes achieved accuracies of approximately 77--82\% and were limited by sparse textual representations \cite{huang2011autoodc, thung2012automatic}. In contrast, LLMs can integrate multiple forms of software engineering evidence, including code structure, test behaviour, and error messages, within a single inference process. Moreover, their ability to perform classification without task-specific labelled training data makes them particularly suitable for applying semantic defect taxonomies such as ODC to large-scale bug datasets.

Existing defect classification approaches primarily rely on bug reports as the source of evidence for classification \cite{colavito2024llm, koyuncu2025exploring, li2024knowbug, du2024llm}. In contrast, our approach integrates multiple software artifacts, including bug reports, source code, failing tests, exceptions, and stack traces, to classify defect types. The use of diverse evidence motivates the need for a well-established and systematically defined taxonomy to constrain and guide LLM-based classification. We therefore adopt ODC as the underlying taxonomy for organizing and interpreting defect types.

\section{The Taxonomy Problem}

While LLMs show promise for defect classification, using them without a structured taxonomy leads to unreliable results. Without standardization, different LLM runs produce different category labels for the same bug \cite{koyuncu2025exploring}. Machine-learning-based bug classification studies also suffer from a proliferation of incompatible taxonomies, which makes it difficult to compare results across studies \cite{andrade2025empirical}. Classification without a principled framework produces vague labels with limited operational value \cite{thung2012automatic}.

Direct evidence that a fixed taxonomy helps comes from \textcite{li2024knowbug}. Their KnowBug framework predicts bug types from deep-learning-framework bug reports, and they compare a prompt that states only the task with one that adds explicit definitions of every label in the taxonomy. Adding the label definitions raises the F-measure from 26.44\% to 33.17\% on TensorFlow, from 29.08\% to 41.39\% on MXNET, and from 17.81\% to 31.14\% on PaddlePaddle. They also found that prompts with an explicit reasoning structure outperformed prompts without one on all three projects.

These findings motivate the use of a well-established taxonomy to constrain and guide LLM outputs. In this thesis, that taxonomy is ODC, and Section~\ref{sec:rq4a} measures the effect of removing it on our own data.

\section{Orthogonal Defect Classification (ODC)} \label{sec:odc}

ODC was introduced by \textcite{chillarege1992odc} as a framework that classifies defects along orthogonal (independent) attributes. It was originally designed to give an in-process signal during active development. The ODC framework defines eight attributes organized into two phases: \emph{opener} attributes recorded at discovery time and \emph{closer} attributes recorded at fix time, summarized in Table~\ref{tab:odc_attributes}.

\begin{table}[!htbp]
    \centering
    \begin{tabular}{l l p{8.2cm}}
        \toprule
        \textbf{Phase} & \textbf{Attribute} & \textbf{Description} \\
        \midrule
        Opener & Activity    & The specific activity being performed when the defect was found, such as code inspection or unit test \\
               & Trigger     & The condition that exposed the defect \\
               & Impact      & The user-visible consequence of the defect \\
        \midrule
        Closer & Defect Type & The semantic nature of the actual correction made \\
               & Target      & Design or Code \\
               & Qualifier   & Missing, Incorrect, or Extraneous \\
               & Age         & Whether the faulty code is base, new, rewritten, or refixed \\
               & Source      & Whether the faulty code is developed in-house, reused from a library, outsourced, or ported \\
        \bottomrule
    \end{tabular}
    \caption{ODC opener and closer attributes \cite{ibm2013odc}}
    \label{tab:odc_attributes}
\end{table}

The central attribute for our work is the \textbf{Defect Type}, which represents the semantic nature of the code correction made to fix a bug. For Design/Code targets, ODC defines seven defect types, which we group into two families. Table~\ref{tab:odc_types} lists them with their definitions.

\begin{table}[!htbp]
    \centering
    \begin{tabular}{l p{9.4cm}}
        \toprule
        \textbf{Defect Type} & \textbf{Description} \\
        \midrule
        \multicolumn{2}{l}{\textbf{\emph{Family: Control and Data Flow}}} \\
        \midrule
        Algorithm/Method & The logic, sequence, or efficiency of a computation is wrong. The fix rewrites how a result is produced, without needing a design change \\
        \addlinespace
        Assignment/\allowbreak Initialization & A value is assigned, initialized, or declared incorrectly, or not at all. The fix corrects a small number of lines of data handling \\
        \addlinespace
        Checking & A validation, guard, boundary test, or error condition is missing or wrong. The fix adds or corrects a conditional \\
        \addlinespace
        Timing/\allowbreak Serialization & Resources are managed incorrectly under concurrency: missing or wrong serialization, locking, or timing of shared-resource access \\
        \midrule
        \multicolumn{2}{l}{\textbf{\emph{Family: Structural}}} \\
        \midrule
        Function/\allowbreak Class/\allowbreak Object & Capability is missing or substantially wrong at the design level. The fix requires a formal design change affecting significant capability \\
        \addlinespace
        Interface/\allowbreak O-O Messages & The defect lies in the interaction between components: parameters, method contracts, or message passing across a module boundary \\
        \addlinespace
        Relationship & An association between objects, data structures, or entities is wrong, such as a conditional dependency between two entities that was not honoured \\
        \bottomrule
    \end{tabular}
    \caption{The seven ODC Design/Code defect types \cite{ibm2013odc, chillarege1992odc}, grouped by this study into two families}
    \label{tab:odc_types}
\end{table}

Two of these types are central to the interpretation of our results. \textbf{Checking} covers a defect in a validation or guard: the program failed to test a condition it should have tested, or tested it incorrectly. \textbf{Algorithm/Method} covers a defect in the computation itself: the program tested the right conditions but computed the wrong result. Many real fixes can be described either way. Adding a bounds check to a loop can be read as supplying a missing guard, or as correcting a computation that should never have gone out of bounds. Although ODC intends its categories to be mutually exclusive, this boundary is difficult in practice. Section~\ref{sec:rq3_changes} shows that it accounts for the majority of the label changes we observe, and Section~\ref{sec:human_agreement} shows that human raters find related boundaries equally difficult.

ODC defect types remain actively used in modern software engineering research. \textcite{esfahani2024understanding} applied ODC to classify defects in LLM-generated code in 2024, demonstrating that the taxonomy generalizes beyond human-written software. The official ODC v5.2 specification from IBM \cite{ibm2013odc} continues to serve as the reference standard for the framework.

\subsection{Impact, and Why This Study Does Not Classify It}
\label{sec:impact}

\textbf{Impact} records the consequence the defect would have for the customer. For an in-process defect, the rater selects the impact the defect would have had if it had escaped to the field; for a defect reported from the field, the impact it actually had \cite{ibm2013odc}. The v5.2 specification defines thirteen values: Installability, Integrity/Security, Performance, Maintenance, Serviceability, Migration, Documentation, Usability, Standards, Reliability, Requirements, Accessibility, and Capability. Two of these cover most ordinary software defects. \textbf{Reliability} covers a failure to perform the intended function without unplanned interruption, and the specification states that severe interruptions such as abnormal termination are always Reliability. \textbf{Capability} covers a defect where the software fails to perform its intended function and satisfy known requirements, but the customer is not affected in any of the other ways.

Impact and Defect Type sit on opposite sides of ODC's two-phase model and describe different aspects of the same defect. Impact is an opener attribute that describes the consequence to the user, while Defect Type is a closer attribute that describes the nature of the correction. A single defect type can produce many impacts, and a single impact can arise from any defect type: a missing bounds check (Checking) might surface as a crash (Reliability) in one context and as a wrong result (Capability) in another.

This study classifies Defect Type only, and no Impact results are reported in this thesis. Impact is judged primarily from the bug report, which describes what a user observed, and Defects4J does not supply bug reports uniformly: availability varies by project and by issue tracker, and is notably lower for projects whose reports are hosted on archived trackers. Assigning an Impact value from a failing unit test alone would mean inferring a customer consequence from evidence that does not contain one. Defect Type, by contrast, can be inferred from the evidence that Defects4J provides for every bug: the code, the failing test, and the fix. Impact classification is therefore left to future work (Section~\ref{sec:future}).

\section{Human Agreement on ODC Classification} \label{sec:human_agreement}

An evaluation of an automated ODC classifier requires some expectation of how consistently the task can be performed. Several secondary sources state that human ODC experts agree with each other roughly 70--80\% of the time.

The available literature instead indicates that agreement on ODC-style classification depends strongly on how much evidence the rater has. Table~\ref{tab:human_agreement} summarizes the relevant studies, ordered by the evidence available to the raters.

\begin{table}[!htbp]
    \centering
    \small
    \begin{tabular}{p{3.6cm} p{3.4cm} p{5.6cm}}
        \toprule
        \textbf{Study} & \textbf{Evidence available} & \textbf{Agreement reported} \\
        \midrule
        \textcite{henningsson2004assuring}, 8 raters, 30 faults & Written fault descriptions only & Mean pairwise $\kappa = 0.16$; merging the two most-confused classes reached only 0.24 \\
        \midrule
        \textcite{hernandez2018crowds}, 5 annotators & Defect report text only & A simple majority was reached on only 481 of 962 and 394 of 675 defects \\
        \midrule
        \textcite{elemam1998repeatability} & Code available at detection time & The scheme is ``in general repeatable'' \\
        \midrule
        \textcite{rahman2020covid}, 2 coders & Full repository context & 72.7\% agreement, $\kappa = 0.70$ (open coding); 95.1\%, $\kappa = 0.93$ (closed coding) \\
        \midrule
        \textcite{agnelo2020nosql} & Full code and change context & $\kappa = 0.93$ for Defect Type \\

    \end{tabular}
    \caption{Reported human agreement on ODC-style defect classification, ordered by the evidence available to the raters}
    \label{tab:human_agreement}

Raters working from written descriptions alone reach $\kappa = 0.16$, while raters with access to the code and the change reach $\kappa = 0.93$. On the Landis--Koch scale \cite{landis1977measurement}, this is a range from slight to almost perfect agreement, determined largely by the evidence available.

This finding is relevant to our study in three ways. First, \textcite{henningsson2004assuring} attribute the low agreement in their study to the limited fault descriptions and recommend providing raters with source code and change information, which corresponds to our post-fix evidence mode. Second, if agreement increases with evidence, the classification that sees the developer's fix is the better-informed one, which supports its use as the reference in RQ3. Third, the most frequent confusion reported by \textcite{henningsson2004assuring} was between Assignment and Algorithm, with Checking and Algorithm third, and Section~\ref{sec:rq3_changes} shows that our own label changes fall within the same group of types.

The confusion counts must be read carefully. In \textcite{henningsson2004assuring}, the most-confused pair was Assignment and Algorithm, and the reported figure of 22 out of 28 refers to rater pairs, not to bugs or classifications. By occasions, the ranking was Assignment--Algorithm 184, Interface--Algorithm 77, Checking--Algorithm 68, Assignment--Interface 59, and Assignment--Checking 49.

\section{Summary}

Despite the growing adoption of LLMs in software engineering, their application to semantic defect classification using the ODC taxonomy remains largely unexplored. Existing defect classification approaches have primarily relied on individual sources of evidence, such as issue reports, code-level features, or repair patches, rather than integrating diverse software artifacts, including bug reports, source code, failing tests, exceptions, and stack traces. Furthermore, there is limited understanding of how effectively LLMs can classify defects into well-defined ODC categories and how different prompting strategies influence classification performance. The lack of ODC defect-type annotations in the widely used Defects4J benchmark also presents a significant challenge for systematic evaluation. These gaps motivate our study to investigate LLM-based ODC defect classification using multiple software artifacts and to systematically compare different prompting strategies for improving the accuracy and reliability of defect-type classification.

\chapter{Proposed Methodology} \label{chapter:proposed}

This chapter describes the design and implementation of our classification pipeline. The Defects4J v2.0 dataset \cite{just2014defects4j} provides over 830 reproducible bugs curated across 17 real-world Java projects. In this research, we classify Defects4J bugs into ODC defect types using an LLM, following three stages: Data Collection, Bug Classification, and Evaluation. The primary goal of this research is to identify and categorize software defects based on their underlying characteristics, thereby providing a structured understanding of the nature and distribution of defects in the Defects4J dataset. The data collection stage prepares and transforms the Defects4J bug data into a suitable representation for classification; the classification stage assigns appropriate ODC types to the identified bugs; and the evaluation stage assesses the performance and reliability of the classification results using appropriate evaluation measures. Figure~\ref{fig:methodology} demonstrates the workflow, and the rest of this chapter describes each stage in turn.

\section{Pipeline Architecture Overview}

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\linewidth]{methodology_overview.png}
    \caption{Overview of the proposed methodology: data collection from Defects4J artifacts into per-bug evidence contexts, ODC classification through the enforced reasoning loop, and evaluation across the research questions}
    \label{fig:methodology}
\end{figure}

The pipeline follows a file-oriented, synchronous architecture with no database, queue, or asynchronous orchestration. Each stage reads and writes structured JSON artifacts, so any stage can be rerun, inspected, or audited independently.


\begin{enumerate}
    \item \textbf{Data Collection:} We build a case file for each bug containing the report, the failing tests, the error messages, and the surrounding code, which is the information a developer would examine before seeing the fix. The output is a structured \texttt{context.json} file per bug.
    \item \textbf{Classification:} The case file is provided to an LLM, which assigns an ODC defect type using one of three prompting strategies, ranging from a single prompt to an enforced, evidence-driven reasoning loop. The output is a \texttt{classification.json} file per bug per condition.
    \item \textbf{Evaluation:} Because Defects4J carries no ODC labels, we classify each bug a second time with the real fix visible, and measure how closely the pre-fix classification matches the fix-informed one.
\end{enumerate}

Two architectural principles hold throughout. First, the pipeline supports multiple LLM providers (Gemini, OpenRouter, Groq, and OpenAI-compatible APIs), so the classification logic is independent of any one vendor. Second, the list of classes modified by the fix is stored as a hidden oracle and never enters the LLM prompt, which prevents the pre-fix classification from accessing fix information \cite{rafi2024revisiting}.

On the opener side (discovery story):
\begin{itemize}
    \item \textbf{Tests} map to \textbf{Activity}, because the test type indicates what was being performed when the defect was found. For Defects4J, this is a unit test in every case.
    \item \textbf{Stack traces} map to \textbf{Trigger}, because the runtime context captured in the trace shows the specific condition that exposed the defect.
    \item \textbf{Bug reports} map to \textbf{Impact}, because they describe the user-visible symptom and consequence, such as a crash or an incorrect result.
\end{itemize}

On the closer side (repair story):
\begin{itemize}
    \item \textbf{Code diffs} map to \textbf{Defect Type} and \textbf{Qualifier}, because the diff reveals the semantic nature of the mistake and how it manifested (Missing, Incorrect, or Extraneous).
    \item \textbf{Modified classes} map to \textbf{Target} and \textbf{Age}, because they show where the fix was applied and, with commit history, when the defect was likely introduced.
\end{itemize}

Two attributes are fixed by the construction of the dataset rather than classified. Target is always Code, because Defects4J bugs are fixed in source and there is no separate design document. Source would be Developed In-House for nearly every project, since these are long-running, community-maintained Java libraries.

This separation follows ODC's design principle that discovery data should not be mixed with repair data \cite{chillarege1992odc}. It also underlies our evaluation: the pre-fix classification sees opener-side evidence, the post-fix classification additionally sees closer-side evidence, and the Defect Type is a closer attribute.

\section{Evidence Collection}
\label{sec:collection}

This section describes how the evidence for the pre-fix and post-fix classifications defined in Section~\ref{sec:prefix_postfix} is collected. To classify a Defects4J bug into an ODC type using an LLM, we prepare two types of files, namely a pre-fix context and a post-fix context, for the buggy and fixed versions of the code respectively. The only difference between these two files is the fix diff, which represents the exact difference between the buggy version of the code and its fixed version. The pre-fix context is the one used for bug classification, without access to any information from the corresponding fix; the post-fix context is used to produce the evaluation reference, where the actual code changes provide sufficient evidence for defect-type classification.

For each bug, we extract and store the following artifacts as the context for the LLM.

\paragraph{Bug identity and Defects4J metadata.} We record the project and bug IDs, the buggy and fixed revision identifiers, the issue-tracker report ID and URL, the modified classes, and the triggering and relevant tests.

\paragraph{Bug report content.} We fetch the original bug report from the issue tracker (JIRA, GitHub, or a generic web page) and store it in full, including its title, labels, and comment thread.

\paragraph{Failing tests, exception, and stack trace.} We check out the buggy revision, compile it, and run the test suite to confirm that the bug reproduces. For each triggering test, we capture its name, the raised exception, the raw stack trace, and a parsed list of every frame with its class, method, file, and line.

\paragraph{Suspicious frames.} A single failing JUnit test typically produces a long stack trace, most of whose frames belong to the test harness (JUnit, TestNG, Hamcrest), the JDK, or the build tool (Ant, Maven). These frames carry no information about the defect. A suspicious frame is a stack frame that points into the project's own source tree. We identify suspicious frames by filtering the parsed frame list against the project's source roots, preserving the original stack order so that the innermost project frame comes first. Suspicious frames serve two purposes: they are the anchor points for snippet extraction, and therefore determine which code the model reads; and their order encodes the call path that led to the failure.

\paragraph{Code snippets.} Around each suspicious frame and each failing test, we extract a short source window with the relevant line marked. Production snippets cover $\pm$12 lines around the frame, and test snippets cover $\pm$18 lines, because a test assertion is usually further from its setup. These snippets provide localized context showing expected versus actual behaviour.

\paragraph{Coverage (optional).} Cobertura coverage analysis can be run on the suspicious classes, and the resulting XML is parsed for line and branch execution rates. Coverage is available to the model as a probe target rather than included by default.

\paragraph{Normalization and deduplication.} Bug report HTML is converted to text, tracker boilerplate is removed, and whitespace is collapsed, so that the same report does not consume a different amount of the prompt depending on its tracker. Repeated frames from recursive calls are collapsed, and a stack-trace prefix shared by several triggering tests is stored once. Code snippets are deduplicated by source range, so two suspicious frames in the same method do not produce overlapping copies. As a result, each distinct piece of evidence appears once in the case file.

\paragraph{Hidden oracles.} We separately store the modified classes as a hidden oracle. This field is excluded from the LLM prompt in both evidence modes and is used only during evaluation, for example to check whether a probe reached the modified class.

\paragraph{Fix diff (post-fix oracle).} For post-fix classification, we also record the buggy-to-fixed source diff. This field is empty in the pre-fix record and withheld from the model otherwise.

\paragraph{Keeping the fix out of the pre-fix evidence.} Two channels can leak fix information into the pre-fix context. The raw Defects4J metadata names the classes the fix modified, and bug reports for resolved issues often discuss the resolution, including status transitions and ``fixed in'' comments. Both are removed from the pre-fix evidence before it is shown to the model, while the post-fix evidence is left unchanged. The two case files therefore differ only in the fix information, which is the difference the pre-fix/post-fix comparison is designed to isolate.

\section{Evidence Modes: Pre-fix versus Post-fix}
\label{sec:evidence_modes}

The pre-fix and post-fix classifications defined in Section~\ref{sec:prefix_postfix} correspond to the two phases of ODC's opener/closer model \cite{chillarege1992odc}, as shown by the artifact mapping in Figure~\ref{fig:odc_mapping}.

\textbf{Pre-fix mode} (the default) corresponds to the opener side. The evidence it uses (stack traces, test failures, error messages, code snippets, and bug report content) describes how the defect was discovered and what went wrong, so the LLM must reason about the defect from its symptoms. Conceptually, this is like a doctor diagnosing a patient from symptoms alone.

\textbf{Post-fix mode} corresponds to the closer side. The buggy-to-fixed diff shows exactly what was changed, which is the evidence ODC uses to record the Defect Type. This is like a pathologist with biopsy results who can see the exact problem.

Because the Defect Type is a closer attribute, the post-fix mode holds the evidence that defines it, while the pre-fix mode must infer it. If the pipeline classifies correctly from symptoms alone, the pre-fix result should therefore broadly agree with the post-fix result.

\section{LLM-based ODC Classification}
\label{sec:conditions}

In the classification stage, Defects4J bugs are classified into ODC types using an LLM. A single prompt combines two separate decisions: the label space the model may answer in, and the way it is asked to reason toward an answer. We separate these into two independent axes, the taxonomy axis and the strategy axis.

\subsection{Taxonomy Axis: How Strict the Vocabulary Is}

The model can answer in three ways:

\begin{itemize}
    \item \textbf{Free:} The model answers in its own words with no fixed list. This setting allows us to measure how much a taxonomy narrows an otherwise unconstrained vocabulary.
    \item \textbf{Closed:} The model must select exactly one of the seven canonical ODC Design/Code types.
    \item \textbf{Open:} The model may select one of the seven types or ``Other''. An ``Other'' answer is accepted only together with a written justification, the nearest of the seven types, and a confidence score, so that every escape is auditable.
\end{itemize}

Whenever a fixed list is used, the model also returns a structured record: the chosen type, close alternatives, the ODC family, a confidence score, and a short reasoning trace. Open is the default taxonomy setting, because we do not force a bug into a fixed schema; a defect that does not belong to any ODC type is recorded as data.

\subsection{Strategy Axis: How the Model Reasons}

\paragraph{Zero: a single plain prompt.} The simplest strategy is one plain prompt with no taxonomy and no examples. It is the unstructured baseline against which the other strategies are measured, and it is taxonomy-free by definition.

\paragraph{Few: one strong, well-prepared prompt.} The second strategy also asks for a single answer, but the prompt is built carefully. It defines every ODC type with example patterns, instructs the model not to default to the general Function/\allowbreak Class/\allowbreak Object type, walks through a short decision checklist before that type may be considered, and includes worked examples chosen for pairs of types that are easy to confuse. This is the strongest single-call prompt we could build, and it is the baseline the third strategy has to improve upon.

\paragraph{Scientific: an enforced reasoning loop.} The third strategy does not allow the model to simply narrate a chain of thought. Instead, the model must commit to a hypothesis, request specific evidence, and evaluate what it receives before concluding. Section~\ref{sec:loop} describes the loop in detail.

\subsection{Valid Conditions}

Not every combination of the two axes is meaningful. A zero-shot prompt carries no vocabulary constraint, and the free setting defines none, so only five of the nine combinations are valid. Figure~\ref{fig:conditions} shows the condition space.

\section{Prompt Design}

Every classification combines a \textbf{system prompt}, which holds the instructions that are constant across bugs within a condition, with a \textbf{user prompt}, which holds the evidence for one bug. Because the full prompts are long, we present them as templates that separate fixed instructions from dynamically filled components \cite{baltes2026guidelines}. Figures~\ref{fig:prompt_few} and~\ref{fig:prompt_scientific} show the templates of the two taxonomy-grounded strategies; the \textit{zero} strategy sends the same evidence with a request to describe the defect in the model's own words and contains no ODC terms.

The highlighted components are defined as follows. \textbf{BUG\_CONTEXT} is the evidence payload of Section~\ref{sec:collection} (sanitized bug report, failing tests with filtered stack traces, suspicious frames, and code snippets, plus the fix diff in post-fix mode), identical for both strategies. \textbf{ODC\_TAXONOMY} gives each of the seven types with its family, definition, indicators, contrastive ``when not to choose'' guidance, and examples, and adds ``Other'' as a justified last resort under the open taxonomy. \textbf{ANTI\_BIAS\_RULES} instruct the model not to default to Function/\allowbreak Class/\allowbreak Object and not to rely on benchmark familiarity, without naming any expected distribution. \textbf{DECISION\_TREE} asks seven diagnostic questions, one per type, with Function/\allowbreak Class/\allowbreak Object last, and \textbf{FEW\_SHOT\_EXAMPLES} are five contrastive worked examples \cite{koyuncu2025exploring}; both appear only in the \textit{few} strategy. \textbf{PROBE\_CATALOGUE} and \textbf{TURN\_SCHEMA} define the evidence requests and per-turn structure of the \textit{scientific} strategy (Section~\ref{sec:loop}). \textbf{OUTPUT\_SCHEMA} is the classification record: type, family, confidence, alternative types with reasons, reasoning summary, evidence used and missing, a human-review flag that the model sets when it judges the evidence insufficient, and, under the open taxonomy, the escape justification.

\section{Scientific Debugging Protocol}
\label{sec:loop}

The scientific debugging protocol is the core reasoning strategy of the \textit{scientific} condition. This section describes its origin and the enforced reasoning loop that implements it.

Our protocol is based on AutoSD \cite{kang2023autosd}, which applies scientific debugging to LLM prompting for explainable fault localization. In AutoSD, the initial failure observation, consisting of the failing test, error message, and code, is provided as the prompt input, and each subsequent iteration runs a cycle of hypothesis, prediction, experiment, observation, and conclusion.

We adopt the AutoSD loop-iteration structure and adapt it from localizing a fault to classifying its type. In our pipeline, the initial failure observation is a summary of the evidence context: the bug report, the failing tests with shortened stack-trace excerpts, the suspicious frames, and a limited number of code snippets and coverage entries. The remaining collected evidence, such as complete stack traces, further source snippets of a class, and full coverage data, is held back. We refer to the full collected evidence for a bug as the \emph{evidence store}; the model can access its held-back part only by issuing probes. On every turn the model must:

\begin{enumerate}
    \item \textbf{Hypothesis:} Commit in writing to a specific claim about the defect type, before seeing any new evidence.
    \item \textbf{Prediction:} State what specific evidence would have to be present if the hypothesis were correct.
    \item \textbf{Experiment:} Request that evidence by issuing one of the probes in Table~\ref{tab:probes}.
    \item \textbf{Observation:} Read what the probe returned. The returned payload is recorded in the transcript, truncated to 2{,}000 characters.
    \item \textbf{Conclusion:} Judge whether the observation supports or contradicts the hypothesis, and either conclude or begin another turn, up to a maximum of six turns.
\end{enumerate}

The model can issue five probes, listed in Table~\ref{tab:probes}. Each probe is executed by the pipeline against the evidence store and returns the recorded evidence; the model cannot see anything beyond what the initial summary and its probes return. If a probe's argument matches nothing, the probe returns the list of available items instead, so the model can correct the request on its next turn, and a probe that repeats an earlier request is not served again.

        \texttt{list\_evidence} & none & An inventory of the available evidence: failing test names, classes with production and test snippets, classes with coverage data, and whether a bug report exists \\
        \texttt{full\_stack\_trace} & test name & The complete stack trace and failure message of the matching failing test \\
        \texttt{snippet} & class name & All source snippets collected for the matching class, including test sources \\
        \texttt{coverage} & class name & The full line and branch coverage data of the matching class \\
        \texttt{bug\_report} & none & The full bug report text, sanitized of fix-related content in pre-fix mode \\
        \bottomrule
    \end{tabular}
    \caption{The evidence probes available to the scientific strategy}
    \label{tab:probes}
\end{table}

Because the model must commit to a prediction before it is allowed to see the evidence that would confirm or refute it, this strategy cannot simply rationalise a first guess after the fact. This distinguishes it from a narrated chain of thought, in which the reasoning and the conclusion are produced together and the reasoning can be written to fit the conclusion.

If the loop reaches its turn limit without concluding, the model is required to conclude from the evidence it has, and this is recorded as a forced conclusion. Every turn, probe, returned payload, and hypothesis revision is written into the classification artifact, so the reasoning chain can be audited. Section~\ref{sec:rq4b} uses these transcripts to measure how often the loop reached the modified code.

\subsection{An Example Turn}

The following abstracted example illustrates the mechanism. Consider a bug whose visible symptom is an assertion failure comparing two numeric values, with a stack trace pointing into a utility method.

\begin{description}
    \item[Hypothesis.] ``The defect is \emph{Checking}: the method does not guard against an empty input range, so it proceeds into a computation that is undefined for that input.''
    \item[Prediction.] ``If this is correct, the method body will contain an arithmetic expression over the range with no preceding emptiness or bounds test.''
    \item[Experiment.] The model issues a probe for the source of the named method, which it has not yet been shown.
    \item[Observation.] The returned snippet contains a bounds test, but the arithmetic that follows uses the wrong comparison operator.
    \item[Conclusion.] The prediction is refuted, because the guard exists. The model revises its hypothesis to \emph{Algorithm/Method} and, on the next turn, probes the failing test to confirm that the expected value is consistent with a corrected operator.
\end{description}

The hypothesis is written down in a specific, falsifiable form before the evidence that refutes it is requested. The observation therefore comes from the evidence store after the prediction is fixed, rather than being generated together with the conclusion. Section~\ref{sec:rq4b} measures the effect of this design.

\section{Classification Pipeline and Validation}

Whatever the model returns is checked before it is used. We confirm that the type is one of the seven canonical names or a properly justified ``Other''; clamp the confidence score into a valid range; recompute the ODC family from the chosen type rather than trusting the model's own family label; and normalize the alternative-type and reasoning fields so that every artifact has the same shape. Transient HTTP errors (429, 500, 502, 503) are retried with exponential backoff. This validation layer prevents a malformed or inconsistent answer from corrupting the aggregate results.

Output filenames are condition-tagged (\texttt{classification.<strategy>-<taxonomy>.json}) and written beside the shared, read-only \texttt{context.json}, so every condition reuses the same evidence and no condition overwrites another.

\section{Evaluation Framework}
\label{sec:eval}

Since Defects4J does not provide ground-truth ODC defect-type annotations, we use the post-fix classification as a fix-informed reference for evaluating the pre-fix prediction. The fix provides additional evidence about the nature of the defect, allowing us to examine whether the classification inferred from symptoms and code context remains consistent when the actual repair is revealed.

\subsection{The Reference Standard}

Because no ODC labels exist for Defects4J, accuracy against ground truth cannot be measured for this dataset. We therefore measure agreement with the best available reference: the post-fix classification, produced by the same model, taxonomy, and prompt on the same bug, with the developer's fix diff added to the evidence. Three considerations support this choice:

\begin{enumerate}
    \item \textbf{The reference sees the evidence that defines the answer.} An ODC defect type describes the nature of the corrective change. The post-fix classification sees that change, while the pre-fix classification has to infer it.
    \item \textbf{It follows the standard design when no ground truth exists.} The comparison is a two-rater design in which the second rater has more information, and Section~\ref{sec:human_agreement} shows that agreement on ODC classification depends on the evidence available.
    \item \textbf{Our data indicate that the post-fix classification is the more stable one.} The human-review flag is raised 16 times in the pre-fix classifications and never in the post-fix classifications, and the two strategies agree with each other more often in post-fix than in pre-fix mode, in every project studied.
\end{enumerate}

Agreement with this reference is not the same as correctness: both classifications can be wrong together, and Section~\ref{sec:manual} gives examples. We therefore interpret agreement as reproduction of a better-informed reference.

\subsection{The Four-Tier Framework}

We compare the pre-fix and post-fix classifications at four tiers, as shown in Figure~\ref{fig:eval_levels}.

\begin{enumerate}
    \item \textbf{Tier 1 --- Strict match:} Do the pre-fix and post-fix classifications assign the exact same ODC type? This is the most demanding metric.
    \item \textbf{Tier 2 --- Top-2 match:} Is the primary type of one classification found among the alternative types of the other? This captures cases where the model identified the type but ranked it second.
    \item \textbf{Tier 3 --- Family match:} Do both classifications fall within the same ODC family (Control and Data Flow or Structural)? This captures broad semantic agreement when the specific type differs.
    \item \textbf{Tier 4 --- Cohen's $\kappa$:} A chance-corrected measure of strict agreement, which accounts for the agreement expected when most bugs fall into a few categories.
\end{enumerate}

Cohen's $\kappa$ is computed as
\begin{equation}
    \kappa = \frac{p_o - p_e}{1 - p_e},
    \label{eq:kappa}
\end{equation}
where $p_o$ is the observed agreement and $p_e$ is the agreement expected by chance alone. It is read on the Landis--Koch scale, where $0.21$--$0.40$ counts as fair, $0.41$--$0.60$ as moderate, and $\kappa \geq 0.61$ as substantial agreement \cite{landis1977measurement}.

\subsection{Reading Tiers 2 and 3}
\label{sec:l3l4}

Tiers 2 and 3 produce high values that are close to their chance level. Because three types dominate the benchmark and all three belong to the same family, randomly shuffling the post-fix labels still yields top-2 and family match rates above 90\%. Reported on their own, these two tiers therefore carry little information. We report them conditional on disagreement: among the bugs where Tier 1 fails, Tiers 2 and 3 describe how far apart the two labels are. Chapter~\ref{chapter:results} uses this reading throughout.

\section{Summary}

The proposed methodology combines three ideas: multi-modal evidence collected from Defects4J into a normalized case file, ODC's principled taxonomy with an explicit escape category, and an enforced hypothesis-and-probe loop adapted from scientific debugging. Separating the taxonomy axis from the strategy axis gives a controlled condition space, and the dual-mode pre-fix/post-fix design provides an evaluation reference for a benchmark without labels. The next chapter describes the experimental setup, and Chapter~\ref{chapter:results} presents the results.

\section{Experimental Setup}

\subsection{Evidence Collection Configuration}

For each bug, the pipeline uses evidence in two modes:
\begin{itemize}
    \item \textbf{Pre-fix:} Symptoms only (bug report, stack traces, failing tests, and code snippets), with no access to the fix.
    \item \textbf{Post-fix:} All pre-fix evidence plus the actual buggy-to-fixed code diff.
\end{itemize}

Stack-frame filtering retains only project source frames, discarding JUnit, TestNG, Hamcrest, JDK-internal, and build-tool frames. Production snippets capture $\pm$12 lines around each suspicious frame; test snippets capture $\pm$18 lines and are limited to the first three failing tests per bug. Coverage analysis is optional and focuses on suspicious classes parsed from Cobertura XML.

Every \texttt{context.json} contains the bug ID, project name, and report URL; failing-test summaries, exception messages, and stack-trace frames; production-code and failing-test snippets; optional Cobertura coverage summaries; hidden-oracle fields (the modified classes and the optional fix diff); and the buggy/fixed revision metadata. The same \texttt{context.json} is read by every condition, so no condition sees different evidence. The context is read-only during classification, and the hidden-oracle fields are stored with the file but never enter the prompt, so the evaluation layer can check what a probe reached without the classifier having access to that information.

\subsection{LLM Configuration}

The classification uses the following configuration:
\begin{itemize}
    \item \textbf{Provider and model:} Google Gemini API, model \modelname, with schema-enforced structured output. This model is used for every classification in the 410-bug study.
    \item \textbf{Second model:} OpenAI \texttt{gpt-5-mini}, accessed through an OpenAI-compatible API with its default temperature and reasoning effort, used for the cross-model analysis (Section~\ref{sec:crossmodel}) of the thirteen manually analysed bugs described in Section~\ref{sec:manual}. Both models use the same evidence contexts and prompts.
    \item \textbf{Conditions:} \textit{scientific-open} (default), \textit{few-open}, and the \textit{zero-free} baseline.
    \item \textbf{Reasoning loop:} At most six turns, with each probe's returned payload truncated to 2{,}000 characters in the transcript.
    \item \textbf{Output format:} Structured JSON with the ODC type, alternative types, family, confidence score, reasoning trace, and, for the scientific condition, the full turn transcript.
\end{itemize}

\subsection{Evaluation Configuration}
\label{sec:stats}

Each bug produces a pre-fix and a post-fix classification per condition, and the pairs are compared using the four-tier framework of Section~\ref{sec:eval}. In addition, the following statistical methods are used in Chapter~\ref{chapter:results}.

\paragraph{Monte Carlo permutation $\chi^2$ test (RQ1).} The standard $\chi^2$ test of association assumes that every cell has an expected count of at least five. Our project-by-type table violates this assumption, because several ODC types are rare. We therefore shuffle the labels across bugs 10{,}000 times and compute the proportion of shuffled tables whose $\chi^2$ statistic is at least as large as the observed one. We report Cram\'er's $V$ alongside the test as a measure of effect size.

\paragraph{Rule of three (RQ2).} When zero events are observed in $n$ trials, the 95\% upper bound on the true event rate is approximately $3/n$. We use this bound to express the absence of escapes as a quantitative limit.

\paragraph{Bootstrap confidence intervals (RQ3).} To quantify the uncertainty of strict match and Cohen's $\kappa$, we resample bugs with replacement 2{,}000 times and report the resulting 95\% percentile interval.

\paragraph{Paired bootstrap on the $\kappa$ difference (RQ4b).} To compare two conditions evaluated on the same bugs, we resample bugs 5{,}000 times, recompute the $\kappa$ of both conditions on each resample, and take the difference. This preserves the pairing and yields a confidence interval on the difference itself.

\paragraph{McNemar's exact test (RQ4a, RQ4b).} For paired binary outcomes, such as whether each bug's pre-fix label matches its post-fix label under two conditions, McNemar's test compares the two discordant counts. Because it counts raw agreement without chance correction, we report it alongside $\kappa$.

\paragraph{Sign test (RQ4b).} A non-parametric test of whether one condition outperforms another consistently across projects, regardless of the size of each difference.

\paragraph{Total variation distance and entropy (RQ1, RQ3, RQ4a).} Total variation distance (TVD) measures how far apart two label distributions are, on a scale from 0 to 1. Shannon entropy measures how spread out a single distribution is, in bits. The vocabulary reduction ratio measures how strongly a taxonomy constrains the labels, and is computed as $1 - k/u$, where $k = 7$ is the number of ODC types and $u$ is the number of distinct labels produced without a taxonomy.

\subsection{Discussion}

A zero escape count could reflect reluctance to use the ``Other'' category rather than genuine coverage. Two observations argue against this interpretation. First, the model did not restrict itself to the dominant types: it selected Relationship 28 times, Function/\allowbreak Class/\allowbreak Object 17 times, and Interface/\allowbreak O-O Messages 13 times across the corpus, so the full label space was in use. Because the open taxonomy produced no escapes, a closed-taxonomy pass could only have measured the effect of prompt wording, and we did not run it.

The finding is therefore that the seven ODC types were sufficient for these six Defects4J projects: the escape category was available and was not used. This does not establish that the seven types are sufficient for all software, since Defects4J represents a specific kind of defect.

\subsection{Statistical Analysis}

Cohen's $\kappa$ of 0.505 indicates moderate agreement on the Landis--Koch scale, below the substantial band that begins at 0.61. The confidence intervals for the two strategies, $[0.433, 0.574]$ and $[0.310, 0.468]$, overlap only slightly.

To interpret these values, we measured the agreement between the two strategies when both are given the fix. With the fix visible, \textit{scientific-open} and \textit{few-open} agree on 76.3\% of bugs ($\kappa = 0.614$); without the fix, they agree on 68.0\% ($\kappa = 0.451$). This holds in all six projects. Two classifications by the same model, both with access to the fix, therefore still disagree on nearly a quarter of bugs. The pre-fix strict match of 70.2\% lies about six percentage points below this level, which indicates that a substantial part of the remaining disagreement reflects ambiguity in the classification task rather than the absence of the fix.

The two strategies also differ in how they disagree. The scientific condition achieves higher strict match and $\kappa$, but when it disagrees, the disagreement is more often severe: 8.2\% of its drifts are unrelated to the reference, compared with 1.5\% for few-shot. The few-shot condition more often lists the reference label as an alternative, whereas the scientific condition commits more firmly to a single type.

\subsubsection{Per-Project Pattern}

The gain from the loop is not uniform across projects. The difference in $\kappa$ is largest for Chart ($+0.323$), Time ($+0.268$), and Mockito ($+0.227$), which are the projects where few-shot is weakest, and smallest for Math ($+0.066$), Closure ($+0.065$), and Lang ($+0.049$). For Time, the few-shot $\kappa$ interval is $[-0.138, 0.530]$ and includes zero, whereas the scientific condition reaches $\kappa = 0.480$. The loop therefore provides its largest benefit where the single-call prompt is least reliable. It does not, however, improve Closure meaningfully, where both strategies perform at a similar, lower level.

This pattern is consistent with RQ1: the few-shot type distribution differs significantly by project ($p = 0.010$), whereas the scientific distribution does not ($p = 0.096$), suggesting that the enforced loop is less sensitive to project-specific characteristics.

\subsubsection{Use of the Loop}

The reasoning transcripts show that the loop is often not fully exercised. Thirty-seven scientific pre-fix classifications, and 126 post-fix classifications, concluded without issuing any probe. The class modified by the fix is present in the evidence store for only 125 of 410 bugs (30.5\%), and for only 13 of the 153 Closure bugs; a pre-fix probe retrieved it for only 64 bugs. Agreement by number of probes is 86.5\% for zero probes ($n = 37$), 69.1\% for one ($n = 136$), 63.8\% for two ($n = 127$), and 73.6\% for three or more ($n = 110$). Since bugs that require no probes are likely easier, probe count reflects bug difficulty rather than causing better agreement.

Evidence coverage alone does not explain the per-project gains: the modified class is absent from the evidence store for every Mockito bug, yet Mockito shows one of the largest gains, while Lang has it for almost every bug and shows the smallest. The significant improvement was nevertheless measured while the modified class was unavailable for most bugs, so the result should be interpreted as a lower bound on what the loop can contribute with more complete evidence.

\section{Why Types Diverge}
\label{sec:divergence}

Pre-fix and post-fix classifications are expected to diverge for a minority of bugs, for reasons intrinsic to semantic classification rather than pipeline error.

\textbf{Evidence asymmetry.} Pre-fix evidence shows what went wrong (the symptoms), while post-fix evidence shows what was changed (the fix), and one underlying defect can produce several symptoms. Human agreement on ODC classification shows the same dependence on evidence: \textcite{henningsson2004assuring} report $\kappa = 0.16$ for raters working from fault descriptions, while \textcite{agnelo2020nosql} report $\kappa = 0.93$ for raters with full code and change context.

\textbf{ODC boundary ambiguity.} Some bugs legitimately sit near a type boundary, most often between Checking and Algorithm/Method, where a missing guard and a corrected computation describe the same defect from two perspectives. In our results, 80.3\% of drifts fall within the three Control and Data Flow types, and 61\% cross the Algorithm/Method--Checking boundary.

% \textbf{Multi-fault contamination.} Co-existing faults \cite{callaghan2024mf} can introduce symptoms from a fault other than the one being fixed.

The four-tier framework makes this structure visible: the gap between strict match and family match shows that disagreement is concentrated on boundary-adjacent types rather than distributed across unrelated families. At the level of aggregate statistics, which is the level at which ODC is designed to be used, the effect of the fix is small, with a total variation distance of 0.051 between the pre-fix and post-fix distributions.

\subsection{S1: Both Modes Agree and Both Are Correct}

\textbf{Chart\_9} shows the pipeline working as designed. The fix widens the predicate \texttt{endIndex < 0} to \texttt{(endIndex < 0) || (endIndex < startIndex)}, so an empty computed range is caught before it propagates. The loop hypothesised a missing guard, probed for the production class, and retrieved it, which occurred for only 64 of the 410 pre-fix loops. The symptom, hypothesis, retrieved evidence, and conclusion are consistent.

\textbf{Lang\_40} shows a correct classification of a non-Checking type: a case-insensitive search implemented with \texttt{toUpperCase} is replaced by an explicit \texttt{region\allowbreak Matches} loop, and all four classifications correctly assign Algorithm/Method.

\subsection{S2: Both Modes Agree and Both Are Wrong}

This scenario shows that agreement between the two modes does not imply correctness.

In \textbf{Chart\_17}, the developer reimplemented \texttt{clone()} so that it no longer delegates to \texttt{createCopy}; the guard on which the model focused is not changed by the fix. Both scientific classifications assign Checking with confidence 1.0, following the location where the exception surfaced rather than what was changed. We refer to this as \textbf{symptom-site bias}. Both scientific classifications concluded at the first turn without issuing a probe.

In \textbf{Math\_90}, the bug report states that the problem ``could be fixed by checking that the object is Comparable'', and this suggestion became the label, even in post-fix mode, where the diff shows an API signature change and the failing test expects a \texttt{Class\allowbreak Cast\allowbreak Exception} that the suggested guard would have prevented. We refer to this as \textbf{bug-report anchoring}.

In both bugs, the few-shot classification changed its label once the diff was visible, while the scientific classification did not. With gpt-5-mini, the scientific pre-fix classification of both bugs was also Checking, concluded at the first turn without a probe, which indicates that these two failure modes are not specific to one model; its post-fix classification corrected Chart\_17 but not Math\_90 (Section~\ref{sec:crossmodel}).

\subsection{S3: The Fix Leads to a Worse Label}

In \textbf{Math\_23}, the fix threads a \texttt{best} point through every iteration of \texttt{Brent\allowbreak Optimizer}. The pre-fix scientific classification correctly assigns Algorithm/Method, but the post-fix classification changes to Assignment/\allowbreak Initialization because the patch introduces a new variable with assignments. ODC classifies coordinated multi-site assignment changes as Algorithm/Method. The few-shot classification did not change.

In \textbf{Math\_17}, a missing range check is added, and its \texttt{else} branch routes out-of-range values to the general multiplication instead of the fast path. Under ODC, a Checking defect remains Checking even when the fix adds a branch, and the pre-fix classification applied this rule correctly, while the post-fix classification changed its label based on the added branch, although its own alternative-types note stated that ``a check is added''. This bug is also the one case in which the developers made two repairs of different types at once (Section~\ref{sec:repair_choice}), so a single-label reference cannot represent the fix completely.

In both cases, the post-fix classification followed the surface form of the patch rather than the taxonomy's definition. This is a limitation of the post-fix reference, and it is one reason RQ3 is seen as reproduction of a reference rather than as correctness.

\subsection{S4: The Fix Leads to a Better Label}

\textbf{Time\_3} is a case of a correct mechanism with an incorrect label. The pre-fix classification described the exact fix, stating that the methods ``do not contain an \texttt{if (amount == 0) return;} guard'', but assigned Algorithm/Method, because it classified according to its explanation of the root cause rather than the nature of the change. The post-fix classification corrected the label to Checking, and both strategies changed in the same way. The developer added the guard to each \texttt{add} method rather than changing the chronology arithmetic itself, which is a repair choice we return to in Section~\ref{sec:repair_choice}.

\textbf{Chart\_11} is a one-token copy-paste error: \texttt{p1.\allowbreak get\allowbreak Path\allowbreak Iterator} should be \texttt{p2.\allowbreak get\allowbreak Path\allowbreak Iterator}. The pre-fix loop used five turns and four probes, never reached the modified class because it is not present in \texttt{context.json}, and still concluded with confidence 1.0. Unsuccessful probes did not reduce the model's confidence.

\subsection{S5: Both Modes Wrong, with Different Labels}

In \textbf{Time\_27}, the pre-fix classification hypothesised an integer overflow while also stating that the value fits in an \texttt{int}, and did not revise the hypothesis. The post-fix classification interpreted an added guard as a structural Relationship defect.

\textbf{Lang\_20} illustrates a limitation of the task itself. A null dereference occurs inside a \texttt{String\allowbreak Builder} capacity estimate. A null guard would be a Checking fix, but the developer instead changed the initial capacity expression so that the dereference no longer occurs, which is an Assignment/\allowbreak Initialization fix. Because ODC classifies the nature of the correction, a bug with more than one reasonable fix can have more than one valid defect type, and a pre-fix classification cannot determine which fix the developer will choose. Section~\ref{sec:repair_choice} collects the bugs in which we observed this.

\subsection{S6: Scientific and Few-Shot on Identical Evidence}

In \textbf{Math\_104}, the fix changes a single constant, \texttt{DEFAULT\_\allowbreak EPSILON}, from \texttt{10e-9} to \texttt{10e-15}. The scientific classification's first prediction named both the constant and the new value, but assigned Algorithm/Method because its hypothesis concerned the convergence algorithm. The few-shot prompt's contrastive guidance, which distinguishes a wrong threshold value from wrong logic, led to the correct label.

In \textbf{Mockito\_26}, \texttt{primitive\allowbreak Values.\allowbreak put(double.\allowbreak class, 0)} autoboxes to \texttt{Integer}, and the fix writes \texttt{0D}. The scientific classification was correct in both modes. The correct label followed from how the hypothesis was phrased (a wrong value) rather than from the probes: four pre-fix probes returned no new information, and the modified class was not in the evidence store.

In \textbf{Chart\_7}, the scientific classification changed from Assignment/\allowbreak Initialization to Algorithm/Method, while the few-shot classification changed in the opposite direction on identical evidence. The scientific pre-fix label is correct, but its stated mechanism, a ``stale cached index'', is not supported by the code; the actual defect is the use of \texttt{min\allowbreak Middle\allowbreak Index} where \texttt{max\allowbreak Middle\allowbreak Index} was intended. A label-only metric scores this classification as correct.

\subsection{When the Developer Had More Than One Option}
\label{sec:repair_choice}

A further reading of the fixes behind the thirteen bugs shows a limit that is not a property of the pipeline but of the reference itself. An ODC defect type describes the nature of the correction that was made, so the post-fix label records \emph{the repair the developer chose}, not the repair the defect required. Where more than one repair was available, the developer's choice, which may be driven by risk, minimality, or the design of the surrounding code, decides the defect type that the post-fix classification can observe. Table~\ref{tab:repair_choice} lists the four bugs in which we found this effect.

Three effects appear in this small set. In Math\_90 and Lang\_20, a Checking repair was available and was not taken: the Math\_90 fix changes the method signature so that the type constraint is expressed by the API rather than by a guard, and the Lang\_20 fix removes the dereference instead of guarding it. In both, the recorded defect type is the one the implemented repair belongs to rather than the one the symptom suggests. In Time\_3, the developer chose the safer of two correct repairs and left the underlying computation untouched, so the recorded type reflects an engineering judgement about risk as much as the defect. Math\_17 is different again: the developers made both a check and an algorithmic change, while our reference assigns one type per bug and can therefore record only one of them.

\paragraph{What the recorded alternatives contribute.} Our classification schema never commits to a single type. Every classification also returns one or two close alternative types, each with a written reason for not being the primary label (Section~\ref{sec:conditions}), and Tier~2 of the evaluation framework is defined over exactly these lists (Section~\ref{sec:eval}). The repair-choice cases show why that design is necessary rather than merely convenient: when a defect admits more than one repair, the type of the repair that was \emph{not} taken is usually the type the classification has already recorded as its alternative. Across the 122 bugs whose label changes once the fix is visible, the post-fix type appears among the pre-fix alternatives for 94 of them (77.0\%), against 36.6\% expected if the post-fix labels were shuffled across the same alternative lists (permutation test, 5,000 shuffles, $p = 0.0002$). Counting these together with the strict matches, the pre-fix classification names the fix-informed type either as its primary label or as a recorded alternative for 382 of 410 bugs (93.2\%).

This does not resolve the ambiguity, and it is not a claim that the pipeline anticipates which repair a developer will choose. The classification reports the type the pre-fix evidence favours and preserves the competing type instead of discarding it, so a reader of the output can see the other repair that was open. The limit is visible in the same set of bugs: the pre-fix alternatives for Math\_90 are Algorithm/Method and Assignment/\allowbreak Initialization, and the interface-level repair the developers made is not among them. Where several repairs are viable, a recorded alternative with a stated reason is more useful for triage than a single label, and it is the form in which our results should be read.

These cases sharpen the interpretation of RQ3. A pre-fix classification cannot know which repair a developer will select, so for bugs of this kind no pre-fix label can be expected to reproduce the post-fix reference, however good the reasoning is. They also bound the reference itself: the post-fix classification is better informed than the pre-fix one, but it is better informed about the repair, not about a defect type that exists independently of it. This is the concrete form of the caveat stated in Section~\ref{sec:human_agreement} and revisited in Chapter~\ref{chapter:threats}, and it is a further reason to read RQ3 as reproduction of a reference rather than as correctness.

\subsection{Findings from the Manual Analysis}

Reading the reasoning transcripts, rather than only the labels, yields the following findings:

\begin{enumerate}
    \item \textbf{Agreement is not correctness.} In S2, both scientific classifications agree with confidence 1.0 and are wrong.
    \item \textbf{The fix can improve or worsen a label.} In S4 it corrects the label; in S3 it leads the model to follow the surface form of the patch instead of ODC's definition.
    \item \textbf{The label and the reasoning can diverge.} Chart\_7 is correct for an unsupported reason, while Time\_3 and Math\_104 identify the right mechanism but assign the wrong label. A label-only metric cannot detect either case.
    \item \textbf{Confidence is not a reliable signal.} Chart\_11 issued four unsuccessful probes and reported confidence 1.0.
    \item \textbf{Some pre-fix labels are underdetermined.} Lang\_20 has two reasonable fixes corresponding to two different ODC types.
    \item \textbf{The loop is not always exercised.} Chart\_17 and Math\_90 concluded at the first turn without probes; in Math\_90, a single probe of the failing test would have contradicted the hypothesis.
    \item \textbf{The reference records the repair, not the defect alone.} In four bugs (Section~\ref{sec:repair_choice}) another repair of a different ODC type was available, and in one of them the developers made two repairs at once, so the post-fix label reflects the developer's choice as much as the defect.
\end{enumerate}

This analysis is a qualitative study of mechanisms and not an accuracy measurement. The thirteen bugs were selected to populate specific scenarios, none of them is from Closure, and the reference reading is the judgement of a single rater applying the pipeline's ODC definitions. Three of the bugs, Time\_27, Lang\_20, and Math\_17, remain open to reasonable disagreement.

\subsection{Behaviours of the Pipeline}

Looking at the classifications of the thirteen scenario bugs from both models, several behaviours appear regardless of the model, which indicates that they arise from the pipeline, the evidence, or the classification task.

\begin{enumerate}
    \item \textbf{The enforced loop outperforms the few-shot prompt in pre-fix mode.} For both models, the scientific condition matches the manual reading for 6 of 13 bugs and the few-shot condition for 4. This is consistent with the RQ4b result that the loop improves pre-fix classification.
    \item \textbf{The fix diff resolves most ambiguity.} With the fix visible, the few-shot condition matches the manual reading for 11 of 13 bugs with Gemini and 12 of 13 with gpt-5-mini, which supports the use of the post-fix classification as the evaluation reference.
    \item \textbf{Symptom-site bias and bug-report anchoring come from the evidence.} Both models assign Checking to Chart\_17 and Math\_90 in pre-fix mode, concluding at the first turn without a probe. The misleading cues, an exception raised by an unchanged guard and a fix suggested in the bug report, are part of the pre-fix evidence, so both models follow them.
    \item \textbf{Some pre-fix labels are underdetermined by the task.} Neither model's scientific classification recovers the developer's Assignment/\allowbreak Initialization fix for Lang\_20, whose symptom is equally consistent with a missing null check.
\end{enumerate}

\subsection{Behaviours of the Model}

Other behaviours differ between the two models, and therefore depend on the model chosen rather than on the pipeline.

\begin{enumerate}
    \item \textbf{Use of the fix diff within the loop.} Gemini's scientific post-fix classification matches the manual reading for 6 of 13 bugs, while gpt-5-mini's matches 11. The limited use of the fix diff by the scientific condition, observed in Section~\ref{sec:manual_strategies}, is therefore a property of the main model rather than of the loop.
    \item \textbf{Depth of investigation.} gpt-5-mini issues almost twice as many probes per scientific run and reaches the six-turn limit on four pre-fix runs, whereas Gemini more often concludes early. gpt-5-mini also changes its scientific label less often between the two evidence modes (5 drifts compared with 8).
    \item \textbf{Which bugs are classified correctly.} Although the two models reach the same pre-fix totals, they share only 3 of their 6 correct scientific pre-fix labels. The model therefore determines which ambiguous bugs are resolved, even when the overall rate is unchanged.
    \item \textbf{Sensitivity of each strategy to the model.} The two models assign the same label in 10 of 13 bugs under the few-shot condition in each evidence mode, but in only 7 of 13 under the scientific condition. Because the loop lets each model choose which evidence to request, its outcome depends more on the model than the outcome of a single static prompt does.
    \item \textbf{Output-format compliance.} gpt-5-mini omitted the confidence field in 18 of its 52 classifications, because the OpenAI-compatible interface does not enforce the output schema as Gemini's structured output does. Model-reported confidence is therefore not comparable across models.
\end{enumerate}

We also examined the effect of gpt-5-mini's reasoning effort setting. On four scenario bugs in the few-shot pre-fix configuration, the default setting matched the manual reading for three bugs and the high setting for two, so increasing reasoning effort did not improve classification.

Taken together, the comparison shows that the main conclusions about the pipeline, the advantage of the loop in pre-fix mode, the value of the fix as a reference, and the evidence-driven failure modes, hold across both models, while the loop's use of the fix diff and its depth of investigation depend on the model.

\chapter{Threats to Validity} \label{chapter:threats}

\section{Internal Validity}

\paragraph{LLM output variability.} LLM classification is non-deterministic. We mitigate this with fixed prompt templates, low-temperature generation where supported, schema-enforced structured output, and a strict post-generation validation layer. The pipeline supports multi-run aggregation, but we did not classify each bug repeatedly, so we cannot report run-to-run variance.

\paragraph{Pre-fix evidence purity.} Two channels can leak fix knowledge into the pre-fix classification if left unsanitised: \texttt{defects4j info} output lists the classes touched by the fix commit, and tracker reports for resolved issues often contain post-fix discussion. Both are removed from the pre-fix payload at classification time (Section~\ref{sec:collection}), while the post-fix payload is left unchanged.

\paragraph{Instrument-prior revision.} Development prompts stated that most Defects4J bugs fall into three named ODC types, which risked biasing the distribution measured in RQ1. This statement was replaced with a neutral anti-default rule that names no expected distribution, and every classification reported in Chapter~\ref{chapter:results} uses the revised prompt.


\section{Construct Validity}

\paragraph{Agreement as a proxy for correctness.} Pre-fix/post-fix agreement is a proxy for correctness, not a direct measure of it, since Defects4J provides no ODC labels. The manual analysis includes bugs that receive the same incorrect label in both modes. This strategy is justified by ODC's two-phase model and by the evidence dependence of human agreement (Section~\ref{sec:human_agreement}), but it cannot substitute for expert-labelled validation.

\paragraph{The reference records one chosen repair.} Because an ODC defect type describes the correction, the post-fix reference captures the repair the developer implemented. Section~\ref{sec:repair_choice} documents four bugs in which a repair of a different ODC type was equally available, and one in which the developers made two repairs of different types while the reference records a single label. For such bugs the pre-fix label cannot be expected to reproduce the reference, and the disagreement measures the space of valid repairs rather than a classification error. This is the reason every classification also records close alternative types with a written justification: for 77.0\% of the bugs whose label changes, the fix-informed type is already present in the pre-fix alternatives, so the competing repair remains visible in the output even when the primary label does not match.

\paragraph{Intended use of ODC.} ODC was designed to provide process feedback from distributions of defect types, not to route individual bugs to developers. Our aggregate-level results support the former use; we make no claim about the latter.

\section{External Validity}

\paragraph{Partial benchmark coverage.} The results cover 410 bugs from six of the 17 Defects4J projects, including 153 of the 174 Closure bugs. The addition of Closure lowered agreement and changed the per-project pattern of the loop's gain, so the results may shift further when the remaining projects are included.

\paragraph{Model dependence.} The corpus-level analysis uses \modelname, and the cross-model analysis uses both \modelname{} and \texttt{gpt-5-mini} on the scenario bugs (Section~\ref{sec:crossmodel}). The cross-model analysis shows that some behaviours, such as the use of the fix diff within the loop, depend on the model, so corpus-level rates may differ for other models.

\paragraph{Language and dataset.} The pipeline is designed for Java and Defects4J. Porting it to other datasets such as Bears or BugSwarm, or to other languages, would require new source resolution and trace extraction, although the classification logic itself is language-independent.

% \paragraph{Multi-fault programs.} \textcite{callaghan2024mf} report that real program versions contain an average of about 9.2 co-existing faults. In pre-fix mode, the model may see symptoms from several faults, while the post-fix diff concerns only one. Part of the measured drift may therefore reflect different faults rather than different interpretations of the same fault, and we cannot currently separate these effects.

\section{Other Threats}

\paragraph{Data contamination.} Defects4J bugs and their fixes are public, and the model may have encountered them during pre-training. We mitigate this by evaluating pre-fix/post-fix consistency rather than absolute correctness, and by retaining full reasoning traces for human review.

\paragraph{Confidence fields.} The model's confidence and human-review fields do not provide a usable signal (Section~\ref{sec:rq3_changes}), so any future filtering or escalation mechanism must rely on other information.

\chapter{Conclusion} \label{chapter:conclusion}

This chapter summarizes our work, discusses its limitations, and outlines future research directions.

\section{Summary}

This thesis presents an automated, evidence-grounded pipeline that classifies Defects4J bugs into ODC Design/Code defect types using an LLM-driven scientific classification approach: an enforced loop of hypothesis, prediction, probe, and observation, inspired by scientific debugging and adapted to classification rather than localization. The key contributions are:

\begin{enumerate}
    \item A two-variable condition space that separates the label space from the reasoning strategy, giving five controlled, comparable conditions.
    \item An open-set ODC formulation with a justified escape category, which turns taxonomy coverage into a measured quantity.
    \item An enforced scientific reasoning loop in which the model must commit to a hypothesis and probe held-back evidence before concluding, leaving an auditable transcript.
    \item A dual-mode pre-fix/post-fix evaluation with a four-tier framework, which provides an evaluation reference for a benchmark without ODC labels.
\end{enumerate}

Together, these address the five limitations of prior work set out in Section~\ref{sec:problem}: coverage through scalable automation, semantic defect-type labels rather than structural or patch-level ones, classification from pre-fix evidence, controlled oracle leakage, and an evaluation framework that does not require ground-truth labels.

Across 410 bugs from six projects and 1{,}640 classifications, three ODC types account for 97.8\% of the bugs, with no significant variation across projects under the default condition. The ``Other'' category was never selected, bounding the true escape rate at 0.2\%. A classification made before the fix exists reproduces the fix-informed reference for 70.2\% of bugs, and is unrelated to it for only 2.4\%. The enforced loop significantly improves chance-corrected agreement over a strong few-shot prompt ($\Delta\kappa = 0.115$) and has the higher agreement in all six projects, although its gain on Closure is not significant. About 30\% of labels change when the fix becomes visible, with 80\% of those changes confined to three closely related types. Running the pipeline with a second model, \texttt{gpt-5-mini}, showed that the pre-fix advantage of the loop and the evidence-driven failure modes are properties of the pipeline, while the loop's use of the fix diff depends on the model.

\section{Limitations}

In addition to the threats discussed in Chapter~\ref{chapter:threats}, the current work has the following limitations:

\begin{itemize}
    \item \textbf{No ground-truth labels:} Defects4J has no ODC annotations, so our evaluation measures reproduction of a better-informed reference rather than correctness.
    \item \textbf{Partial benchmark coverage:} The results cover 410 bugs from six of the 17 projects.
    \item \textbf{Model coverage and single run:} The corpus-level results are produced with one model and the cross-model analysis with two, and each model classifies each bug once per condition, with no consensus mechanism.
\end{itemize}

\section{Future Work}
\label{sec:future}

Several research directions could extend and improve this work:

\begin{enumerate}
    \item \textbf{Human reference labels:} Have at least two raters independently label a random sample of bugs from the fix diff, without seeing model output, and use the adjudicated labels to evaluate both evidence modes.
    \item \textbf{Evaluation of reasoning:} Grade the reasoning trace separately from the label, since the manual analysis shows that the two can diverge.
    \item \textbf{Multi-model evaluation and consensus:} Apply the cross-model analysis to the full corpus and to additional LLMs, and aggregate classifications from several models to reduce single-model variance \cite{colavito2024llm}.
    \item \textbf{Complete ODC attribute set:} Classify Impact (Section~\ref{sec:impact}) for bugs whose reports contain sufficient usage detail, derive Trigger and Activity from the same reports using the specification's mapping \cite{ibm2013odc}, and recover Age from project commit history.
    \item \textbf{Full-dataset and cross-dataset extension:} Complete the remaining Defects4J projects to produce a fully ODC-labelled version of the benchmark, adapt the pipeline to other benchmarks and languages, and use classifications to guide automated program repair \cite{durieux2018automatic}.
\end{enumerate}

\section{Closing Remarks}

Defect classification is a fundamental building block of software quality assurance, and it has traditionally required expensive manual analysis. This thesis shows that ODC defect-type classification of Defects4J can be automated at benchmark scale using LLM reasoning, with an escape category that allows the taxonomy's coverage to be measured and an evaluation reference that does not require ground-truth labels. The results indicate that requiring the model to gather and evaluate evidence before answering improves the reliability of its classifications, particularly on projects where a single prompt is least reliable, and that LLM-driven ODC classification is a promising direction for making defect analysis faster, more consistent, and more informative.
